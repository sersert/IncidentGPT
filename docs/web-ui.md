# Веб-интерфейс

Для первого запуска используйте [пошаговое руководство](getting-started.md).
Для дежурного внутри приложения есть раздел «Руководство» (`/help`).

## Светлая и тёмная темы

Кнопка с солнцем или луной в шапке переключает тему. Она доступна и на телефоне,
управляется клавиатурой и сообщает следующую операцию screen reader.
Выбор сохраняется в браузере, применяется после перезагрузки и синхронизируется
между вкладками этого сайта. Если ручного выбора ещё нет, интерфейс следует
системной теме и её изменениям. Ручной выбор имеет приоритет.

Тема применяется до запуска приложения. Графики, таблицы, формы и диалоги меняют
цвета без перезагрузки и без сброса открытых редакторов. Если браузер запретил
хранение настроек, переключение работает в открытой странице, но не сохраняется.

## Навигация и рабочие экраны

На десктопе разделы доступны в боковой панели; на узком экране меню открывается
кнопкой в шапке. Оно закрывается по Escape и возвращает фокус к кнопке.
Ссылка «Перейти к содержимому» помогает пропустить навигацию с клавиатуры.

«Обзор дежурства» показывает доступные измерения и до 10 активных инцидентов,
упорядоченных внутри этой выборки по критичности и времени. Ссылка «Вся очередь»
ведёт к полному списку. Ошибка API показывается как неизвестное состояние.

В очереди есть поиск по названию/анализу, фильтры статуса и критичности и переходы
по страницам из 25 записей. Условия сохраняются в URL; ссылку можно передать коллеге.
`/` переводит фокус в поиск, Escape очищает строку; поле имеет постоянную подпись
для screen reader. Число результатов относится к текущим условиям, а не ко всем
инцидентам в системе.

Карточка разделена на четыре рабочие вкладки:

| Вкладка | Что в ней |
| --- | --- |
| Обзор и анализ | Алерты, события, логи, анализ и evidence, жизненный цикл, журнал действий и контекст. |
| Расследование | Изменения/покрытие, проверки чтения, зависимости и корректировка состава группы. |
| Решения и runbooks | Подтверждённые решения, различия сред/версий и редактор решения. |
| Отчёты и передача | Версии постмортема и передачи смены, правки, review и экспорт. |

Выбранная вкладка хранится в `?view=investigate`, `?view=knowledge` или
`?view=reports`; без параметра открывается обзор. Стрелки влево/вправо, Home/End
переключают вкладки и фокус. Вкладки сохраняют открытые редакторы при переключении
внутри карточки. Данные раздела загружаются при первом посещении; открытый раздел остаётся смонтированным при последующих переключениях. Это не автосохранение: перед уходом на другой экран или
перезагрузкой страницы сохраните черновик. Ошибка назначения не закрывает форму
и не выдаётся за успешное сохранение.


Кроме доставки в Telegram инциденты можно смотреть в браузере. За это отвечают
два компонента, оба входят в общий чарт:

- **backend** — принимает группы алертов от enricher, хранит инциденты и передаёт
  их дальше в ai-worker;
- **ui** — сам интерфейс, nginx со статикой и прокси на backend.

Оба отключаются через `enabled: false` — тогда остаётся прежняя связка с выводом
только в Telegram.

## Legacy путь backend (по умолчанию)

Backend стоит **в разрыве группового пути**, а сырой фид идёт напрямую:

```
raw-алерты  → ai-worker                            (фид в Telegram не меняется)
группы      → backend → ai-worker /incident-group  (инциденты появляются в вебе)
разбор      → backend                              (обратный канал, см. ниже)
```

Поэтому в values enricher нужно переключить только групповой путь:

```yaml
incidentgpt-enricher:
  env:
    groupBackendUrl: "http://incidentgpt-backend.incidentgpt.svc:8080/api/v1/ingest"
```

Backend передаёт тело дальше **как есть**, на тот же эндпоинт, который enricher
звал напрямую — разбор в Telegram работает как прежде.

### Обратный канал

Ai-worker по умолчанию публикует разбор только в Telegram, и веб о нём не узнает.
Чтобы разбор появился в интерфейсе, укажите ему адрес приёмника:

```yaml
ai-worker:
  env:
    ANALYSIS_CALLBACK_URL: "http://incidentgpt-backend.incidentgpt.svc:8080/api/v1/incidents/by-group/analysis"
```

Без переменной поведение прежнее — компонент остаётся самодостаточным.

## Алерты и инциденты — разные сущности

**Алерт** — единица сырого потока от Alertmanager. **Инцидент** — группа
связанных алертов с одним разбором. Один к одному они не соответствуют: у
инцидента может быть два десятка алертов, и часть из них разбор пометит шумом.

В интерфейсе это два раздела: «Инциденты» и «Алерты», где видно, какой алерт в
какую группу попал, а какой не собран вовсе.

## Хранение

Инциденты живут в Redis — том же, что enricher использует для корреляции. Он
входит в чарт отдельным сабчартом и ставится вместе со всем остальным: один
узел, без репликации и sentinel, с диском на 2 Gi.

Свой Redis подключается так:

```yaml
incidentgpt-redis:
  enabled: false

incidentgpt-backend:
  env:
    REDIS_ADDR: "redis-master.infra.svc.cluster.local:6379"
incidentgpt-enricher:
  env:
    redisAddr: "redis-master.infra.svc.cluster.local:6379"
```

Адрес правится в двух местах: enricher и backend ходят в Redis независимо.

Вытеснение намеренно выключено (`maxmemory-policy` остаётся `noeviction`): с
любой политикой `allkeys-*` Redis под нагрузкой начал бы выбрасывать инциденты,
а это хранилище, а не кэш.

Без Redis сервис всё равно работает, но держит состояние в памяти: **любой
рестарт пода очищает историю**. Для чего-то серьёзнее демо этого мало — под
архив и обучение нужна нормальная база.

## Доступ

По умолчанию остаётся прежний **Basic-вход nginx** (`incidentgpt-ui.authMode: basic`):
существующий htpasswd и Basic-клиенты работают после обновления без новых Secrets.
`auth.enabled` и `auth.existingSecret` относятся к этому режиму. Secret чарта не
создаётся при внешнем htpasswd. Новый образ UI совместим со старым backend в basic.

Страница входа с серверными сессиями — отдельный opt-in. Обновите UI и backend
одним проверенным кандидатом и задайте:

```yaml
incidentgpt-ui:
  authMode: session
  # CIDR именно ваших ingress/reverse proxy, не произвольных клиентов.
  trustedProxyCIDRs: ["10.42.0.0/16"]
  realIpHeader: X-Forwarded-For
  loginBurst: 20
incidentgpt-backend:
  browserSessions:
    enabled: true
  readerAuth:
    existingSecret: incidentgpt-reader
```

CIDR в примере замените адресами ingress своей установки. По умолчанию список
доверенных прокси пуст: нельзя подделать адрес через произвольный X-Forwarded-For.
Без настройки доверия лимит POST-входов разделяется клиентами одного прокси.
Лимит не применяется к проверке сессии и выходу. `/auth-config.json` публично
сообщает только `basic|session`, без operational data и credentials.

Reader Secret содержит исходные `username` и `password` для `TIMELINE_READ_*`.
При использовании `changes.existingSecret` пароль берётся из `timeline-read-password`,
а пользователь — из `TIMELINE_READ_USER`; оба пути Secret одновременно запрещены.
Umbrella-чарт отклоняет session без backend, включённого browserSessions и reader
credentials. Сами значения ключей Secret проверит Kubernetes при запуске pod.

Вторая учётная запись «только просмотр» — опционально: `incidentgpt-backend.viewerAuth.existingSecret`
с ключами `username`/`password` (`VIEWER_USER`/`VIEWER_PASSWORD`). Viewer входит
на той же странице, видит всё, что administrator, а любой не-GET запрос к `/api/`,
кроме входа и выхода, получает 403 в backend — и по cookie, и по Basic. Ответ
`/auth/session` содержит `role: "viewer"`, UI показывает «Только просмотр»; кнопки
действий остаются, но их запросы отклоняются. Cookie viewer понижает роль и при
постороннем `Authorization`. В режиме basic viewer нужно добавить и в htpasswd nginx
**с тем же паролем, что в Secret**: backend узнаёт viewer только по точному совпадению
пары, иначе пропущенный nginx пользователь считается administrator. `VIEWER_USER`,
равный `TIMELINE_READ_USER`, выключает viewer с предупреждением в логе. Смена пароля
viewer отзывает только его сессии. Это не разделение tenancy: viewer читает те же
инциденты, настройки и evidence, что administrator (секреты интеграций в GET маскируются).

В session HTML/стили/скрипты публичны, `/api/` и `/ws/` закрыты `auth_request`.
Случайная HttpOnly/Secure/SameSite=Strict cookie действует восемь часов. Пароль
не записывается в браузер и не подставляется в Authorization внутренних запросов:
после проверки в контексте хранится только principal, который используют auth и audit.
Любые изменения через cookie требуют доверенный Origin, включая старые API.
Basic API-клиенты session-режима сверяются с backend reader credentials.

Redis хранит `igpt:session:<SHA256(cookie)>` с TTL восемь часов: token-bound
`HMAC-SHA256(user\0password, cookie)` и срок действия. Дамп не содержит отдельного
офлайн-проверяемого хеша пароля. Выход удаляет запись; смена credentials отзывает
старые сессии. Клиент сессий переподключается независимо от durable-режима, включая
поздний старт Redis. При настроенном, но недоступном Redis возвращается 503; тихого
перехода на локальные сессии нет. Только отсутствие `REDIS_ADDR` разрешает ограниченную
память одного процесса. Для нескольких реплик нужен общий Redis.

Для HTTP изолированного preview можно задать `BROWSER_SESSION_SECURE=false` в
`incidentgpt-backend.env`; production использует HTTPS и значение true. Новый UI
в session со старым backend несовместим (auth-check даст nginx 500); сначала
обновите оба образа и reader Secret. Для отката верните `authMode: basic` и
`browserSessions.enabled: false`, сохранив старый htpasswd Secret. Старые preview-ключи
`browser-session:*` новая версия не читает; они исчезают по прежнему TTL.
Данные инцидентов не мигрируют. Backend/Redis остаются приватными под NetworkPolicy.
Для независимой проверки старых API сохраняется `LEGACY_API_AUTH_REQUIRED=true`.
`/healthz` остаётся публичным. Не выводите Secrets или rendered YAML в CI/MR.

## Источники данных

Формы находятся в разделе «Интеграции». Фактический сбор требует настройки
совместимого backend/enricher и доступного источника; сохранённая форма сама по
себе его не включает. Формы разделены по
назначению и совместимости API, а не по названию продукта:

| Категория | Тип | Кто подходит |
|---|---|---|
| Метрики | Prometheus API | Prometheus, VictoriaMetrics, Thanos, Mimir |
| | Zabbix API | Zabbix |
| Логи | OpenSearch / Elasticsearch API | OpenSearch, ELK |
| | Loki API | Loki |

VictoriaMetrics отдельной интеграции не требует — достаточно указать её адрес.
Подробнее про логи: [logs-enrichment.md](logs-enrichment.md).

Kubernetes и Telegram настраиваются вне интерфейса: первый работает через service
account пода, второй — через окружение ai-worker. В интерфейсе для них показано
только состояние.

## Что показывает интерфейс

- **Инциденты** — список групп с числом склеенных алертов и краткой сутью разбора
- **Инцидент** — состав группы, отброшенный шум с причиной, разбор целиком, логи
  из хранилища, контекст (namespace, под, нода, деплой), журнал действий
- **Алерты** — сырой поток и привязка к инцидентам
- **Дашборд** — что горит, к чему идти первым, жив ли AI-пайплайн, шторм или норма
- **Аналитика** — поток алертов, самые шумные источники, качество разбора
- **Прогнозы** — ресурсы, которые упрутся в предел, если тренд сохранится
  (использует настроенный Prometheus), и загрузка нод по отдельности

## Новые рабочие процессы

В карточке инцидента есть Recent changes с покрытием и временем источника; история
версий анализа с доступными evidence и отсутствующими данными; подтверждённые
решения и локальные runbook excerpts; ограниченные проверки чтения; типизированные
зависимости и перенос/отделение алерта; события жизненного цикла; postmortem и
передача дежурства. Каждый новый запрос различает загрузку, отсутствие записей,
ошибку и отказ в доступе. Ошибка источника не означает «здоров» или «нет инцидентов».

Для новых API backend самостоятельно проверяет TIMELINE_READ_USER/PASSWORD.
Настройте тот же общий admin, что у nginx; Authorization проксируется. X-Auth-User
не является подтверждением личности. PATCH назначения/статуса теперь тоже требует
эти credentials. Это общий административный доступ, без изоляции команд.

Durable режим не использует старый callback по namespace/group key: backend вызывает
`/v1/analyze` с уникальными incident/analysis ID и сохраняет результат по lease.
Коллекторы/диагностика/генерация включаются отдельно, данные не появляются от одной
формы конфигурации. Подробные параметры: [операционные руководства](../README.md#evidence-durable-jobs-and-investigation-workflows).

Перенос сохраняет исходную страницу/evidence/анализ; устаревшая композиция отмечена
в истории. После переноса обновите контекст. Отчёты имеют версии и CAS revision:
новая генерация не перезаписывает человеческие правки, конфликт требует reload.
Preview отключает raw HTML/images и опасные ссылки; Markdown можно скачать вместе
с action items (ответственный, статус, срок). Генерация не отправляет сообщений.

Восстановление подтверждается отдельно человеком по доступному evidence и известному
времени. Resolved от Alertmanager не доказывает восстановление сервиса. Дашборд и
аналитика показывают обработку AI, принятие, проверенное восстановление и
административное закрытие отдельно; неизвестные значения не заменяются нулём.
Выборки ограничены, показывают число событий и отсутствующих измерений.

## Тестирование моделей

Раздел `/evaluation` содержит библиотеку неизменяемых кейсов и сравнение 1–4 конфигураций модели. Кейс можно создать из выбранной версии анализа или собственного сценария. Эталон не передаётся модели; оценки выставляет инженер. Запуски выполняются явно, без уведомлений и изменения текущего инцидента. Настройка, ограничения и проверка: [Model evaluation lab](model-evaluation.md).
